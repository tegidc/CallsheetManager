Things that were quietly broken

WhatDetail
Six headings were rendering in the wrong font The stylesheet has no rule for h4 headings at all, so anywhere one had been used it fell back to the browser's default serif rather than the app's own label style. It affected the three headings on Budget's Costs tab (Catering / Travel / Hotel), the two on the Hotel summary, and "Dietary requirements" on the catering export. They now use the app's proper heading style. This is the most visible change in the whole phase.
The same styling copy-pasted seven times Seven collapsible section headers each carried an identical hand-written style patch — and half of it (font-size:15px) did nothing at all, because the style it was overriding was already 15px. That's a strong sign the pattern had been copied forward without anyone knowing what it did. It's now one named style used by all seven. Pixel-identical, just no longer seven copies.
Dead leftovers in Tasks and AI Scan Both sections had copied a naming convention from the older collapsible sections without the machinery that actually uses it, leaving tags that nothing ever read. Removed. I checked the Hotel/Catering/Travel summaries carefully — theirs are real and were left alone.
The code map was wrong in three places MAP.md described one shared function's inputs in an order that no part of the app has ever used — documented that way twice. And two notes still referred to Preview & Export by its old code (T-6.x) from before Budget took that number; one line contradicted itself. All corrected against the real code.

The one addition — filter Budget by day

You can now tick which shoot days to cost. No ticks means the whole project, exactly as before. It sits above the Per Department / Per Day / Per Person / Costs switcher rather than inside it, because it changes what all four of those are showing, not just one.

I checked the arithmetic rather than trusting it: on ROW 2026, costing each of the six days on its own adds up to exactly the full project total (£50,510), and a two-day selection came out at £18,730 — the two days' figures added together. So nothing is double-counted or dropped, including the hotel night before Day 1, which only gets charged when Day 1 itself is selected.

  • No unused or orphaned functions anywhere in the app.
  • Budget doesn't keep its own copy of the hotel / catering / travel costs — it genuinely reads the same records those tabs own, so there's nothing to drift apart. Same for the Costs tab.
  • The Crew toolbar and filter panel really are built once and shared identically across all five Crew tabs (Roles / Days on site / Hotel / Travel / Catering) — that held up.
  • Every tab, every Crew view and every Budget view was opened in a browser against your real ROW 2026 data. No errors.

Part 3 — proposal: multi-user collaboration (AL)

This is deliberately a separate proposal, not a recommendation in the table above — it's a different order of work, and it changes assumptions the whole app currently rests on.

The honest starting position

Right now the app has no concept of a user at all. There is one hardcoded company, no login, and every browser that opens the URL reads and writes the same shared database with the same permissions. That isn't a gap to be patched — it's the foundation the current design sits on, and it's why so much of the app is pleasantly simple.

There are two specific things that will bite the moment a second person is editing:

  • Last-write-wins on whole lists. Saving anything writes the entire collection back — all crew, or all projects. If you and I both have the app open and I add a crew member while you rename a project, whoever saves second silently erases the other's change. This is the single biggest risk and it exists today, even without a login screen, any time two tabs are open.
  • Screens don't know when data changed. Everything renders from an in-memory copy loaded at startup, so another person's edits simply won't appear until the page is reloaded.

A staged route, cheapest first

Stage 1 — Stop the silent overwrites. M
Before it matters who anyone is, make saving safe. Two options: either write only the record that changed rather than the whole list, or keep a version number on each collection and refuse a save that's based on a stale copy, reloading and reapplying instead. This is worth doing on its own merits even if multi-user never happens — it's a real data-loss risk today with two tabs open.
Stage 2 — Live updates. M
Supabase can push changes to every open browser as they happen. Subscribe, and refresh the affected screen when something changes underneath you. Once Stage 1 is done this is mostly plumbing, and it makes the app feel collaborative before any accounts exist.
Stage 3 — Actual accounts. L
Supabase has login built in, so the sign-in part is not the hard bit. The hard bit is that every record then needs an owner and access rules, which is a change to every table and every read the app makes. Worth doing properly in one pass rather than half-adding it.
Stage 4 — Roles and permissions. L
The realistic need isn't "admin vs. user", it's that crew day rates and private contact details shouldn't be visible to everyone on the call sheet. Note the app already has a "Private" section on the crew form — that's the natural seam. A sensible first cut is three levels: Producer (everything, including Budget), Crew (their own details plus the schedule), View-only (the call sheet, nothing else).
Stage 5 — Per-company branding. M
Already noted as parked in your own docs. Only becomes real once someone outside Little Film uses it, and it depends on Stage 3 — a logo needs an account to belong to.

What I'd actually suggest

Do Stage 1 now, as its own small piece of work, and stop there for the moment. It removes a live data-loss risk, it's invisible when it's working, and it doesn't commit you to anything. Stage 2 is a nice follow-on. Stages 3–5 are a genuine project and I'd only start them when there's a real second person who needs access — building a permissions model for a hypothetical user is how apps get complicated for no return.

One caveat worth knowing. The AI Scan feature talks to Claude through a server function that requires an API key to be set by hand. If that's never been set, AI Scan will fail at the moment someone tries to use it rather than telling them up front — see recommendation R14 in the table above.
