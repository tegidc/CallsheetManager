G · Structural

Part 3b — What would make Views cheap later

The headline, stated plainly so it can't get lost: nothing needs restructuring yet. Revisit when Budget is real. There is no view infrastructure to build, no abstraction worth extracting today, and no pattern currently in the app that would actively obstruct a second tool. That is the honest answer and I'd rather give it than a speculative redesign. What follows is the reasoning, plus the three cleanups above that would also pay off later — and the one thing that genuinely does need deciding before a second tool writes anything.

The single file: at what point does it stop working?

7,747 lines — 883 CSS, 6,810 JS, 440 functions, 473 KB. That is large, and the instinct is to say it's past due for splitting. I don't think it is, and the reasons are specific rather than sentimental.

The single file is buying real things here. There is no build step, so the deployed artefact is the source — what you read is what runs on github.io, with no sourcemap indirection and no way for the two to drift. Every function is in one scope, so the "canonical lookups" discipline MAP.md enforces (crewById(), projectDays(), resolveCrewRate()) actually holds — there's no module boundary tempting anyone to re-derive a lookup locally rather than import it. And a single grep answers "who touches this field", which is exactly the question this audit kept needing to answer and could always answer cheaply.

What would make it stop working is not line count, it's whether one person can still hold the whole thing in view. The signals to watch for, none of which are firing yet:

  • Duplicate implementations reappearing because nobody knew the first one existed. This is the real cost of size, and it is starting — G7, G8, G9 and G10 are all "somebody wrote a second copy of something". But they're small and local, not structural. Fix them and the signal resets.
  • Editing tool struggling with the file. Not yet an issue at 473 KB.
  • Two people editing it at once. This is the one that would force the issue, and it's the same conversation as multi-user — not a Views conversation.

If the day comes, the least disruptive path is not a bundler. It is splitting the <style> block into app.css and the <script> block into two or three plain <script> files loaded in order — no modules, no imports, no build. Everything stays in one global scope, so not a single call site changes; the only thing you lose is the single-file property, and the only thing you must get right is load order. That is a two-hour change available at any time, which is precisely why it should not be made pre-emptively.

What is genuinely shared vs. Production-specific — and is the boundary visible?

It is partly visible, and the part that isn't is the interesting bit.

Cleanly shared already, and would be shared by any view: the storage layer (loadDB/saveDB/mergeDB/applyMergedDB, ~100 lines, knows nothing about call sheets); the two databases and their canonical lookups; the design system entirely — the four type tokens, six tint tokens and applyAppSettings()'s "write the token the stylesheet already declares" mechanism is genuinely view-agnostic, and it is the strongest piece of architecture in the file; the collapse idiom; esc/val/setv/uid/fmtDate/copyText/flashStatus; the department/role/seniority taxonomy; and the undo mechanism.

Genuinely Production-specific: shoot days as a concept, the schedule editor, camera designations, call sheet assembly, the WhatsApp/Excel outputs.

Tangled, and this is the honest answer to the question: Budget is not actually separable today, because it doesn't own its own data. Every figure Budget shows is read from somewhere else — p.cateringCosts lives with Catering, p.transportCosts with Travel, p.hotelCosts with Hotel, loc.fee on the location record, and days-worked is derived from d.positions, which is the call sheet's own data structure. That is a deliberate and good decision for a cost-visibility screen, and MAP.md is right that it's what keeps every view reconciling. But it means the current Budget tab is a projection of Production's data, not a separate concern that happens to live in the same file.

So the split you're planning is the right one, and for a better reason than "it's getting big": a real Budget tool needs line items, quotes, POs, actuals-vs-estimate — data this app has nowhere to put and shouldn't grow a place for. Building it separately isn't deferring an integration, it's recognising that the two tools own different data. When it links back in as a view, the honest relationship is Budget reads Production's crew/day/cost data; Production reads none of Budget's. One-directional. Worth writing down now, because it's much easier to hold that line from the start.

What would a second tool reading the same app_data need, in order not to corrupt this one?

This is the one part of Part 3b with a concrete answer, and it needs deciding before the second tool writes anything — not after.

R18's guarded write is necessary and not sufficient for two tools. It protects two instances of this app because both sides run the same mergeDB() with the same per-record merge rules. A second tool gets none of that for free. Specifically:

  • The guard is per-key, and a key is a whole collection. db:projects is one row holding every project. A Budget tool that touches one project's cost fields takes the write lock on all of them, and on every unrelated field of every project — crewIds, tasks, travelMethods, the lot. Under any concurrency that's a lot of contention over data it never looked at.
  • A second tool must implement the same merge, or it will lose edits. Not "should" — must. If Budget does a plain upsert on a failed guard, or simply retries, it silently discards whatever this app wrote in between. mergeDB() is 30 lines and is the actual contract between the two tools.
  • Deletion semantics are the sharp edge. mergeDB() only honours a deletion "against a side still matching base". Two tools with different ideas about that will resurrect records.
  • Arrays of bare strings don't merge at all — db:travelmethods and db:coprocompanies are last-writer-wins by design, which is fine for two tabs of one app and is a data-loss bug the moment a second tool edits them.

The cheapest thing that makes this safe is not a rewrite. It is: (a) give Budget its own db: keys for the data it owns, so the two tools' write paths barely intersect; (b) treat the fields Budget reads from this app as read-only on Budget's side; and (c) if Budget must write back — the day-rate override is the obvious candidate — port mergeDB() verbatim rather than reimplementing it. G13 matters here: DB_OBJECT_KEYS is already missing one of its four object-shaped keys, and that inconsistency is currently harmless only because the init guards happen to catch it. A second tool won't have those guards.

Which of today's cleanups also make Views cheaper

Three, and only three. The rest are worth doing on their own merits but have nothing to do with Views:

  • G2 — one collapsible-section builder. The single highest-leverage item on this page for a four-view future. Every view is a stack of collapsible sections; right now every screen re-invents the header.
  • G3 — a spacing scale. A second tool built against the same design system needs to be able to copy the system. Type tokens and tint tokens are copyable today; ~107 hand-written inline margins are not.
  • G13 — DB_OBJECT_KEYS. Tiny, but it's a correctness statement about the storage contract, which is the one thing a second tool has to share exactly.

Explicitly not recommended: a view registry, a router abstraction, a shared-component library, a state container, or extracting anything into modules. Nothing about Preproduction or Edit is specified, and an abstraction shaped for imagined requirements is worse than none.
