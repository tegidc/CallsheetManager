What changed, and why

1
Crew opens on Roles

Instead of Production. A one-line change to the default — crewGridView starts at 'roles'.

2
The Budget's summary bar comes to Roles, unchanged

The same three headline figures, the same phase stack, the same Itemize VAT / Split kit & labour / Costs PP cluster. Not a lookalike — the actual budgetSummaryBarHTML(), so a change to one is a change to both and the two screens can never quote different totals.

3
£££ is the one money switch

Off: Roles is the staffing screen — who is on this job, in which stages. No totals bar at all, because with the money hidden it has nothing to say.

On: the totals bar appears and the money columns come with it — TOTAL, Day rate, Subtotal, VAT reg., VAT, plus Kit / Labour / Est. Costs behind their own toggles. That is the merge you asked for: one control, not a £££ here and a separate set of Budget toggles there.

4
Pre-Prod / Production / Post become filters as well as costing scopes

Those three rows already decide what the Budget costs. Now they also decide who is on screen: switch Production off and the shoot-only crew leave the list. The state is budgetScope — the same object the Budget tab reads — so ticking here re-costs the Budget too. There is precedent: the Crew tab's department filter and the Budget's are already one shared filter, for exactly this reason.

One rule that has to hold: somebody in no phase at all always stays visible, whatever is selected. Roles is where you put them into a stage, so it must never hide the row that holds the control. Watch Nina Roche — she has no prep, no shoot and no edit, and she never disappears.

5
Shoot gets tidy — two modes instead of one crowded column

Normally Prep · Shoot · Post are three plain day counts. Prep and Post stay typeable exactly as they are today; Shoot is read-only, because shoot days get ticked day-by-day on the Production tab. No checkbox, and no small number riding beside it — that is the thing you couldn't name, and it was the checkbox and the count sharing one cell.

Stage mode turns those same three columns into one checkbox each: is this person in pre, in the shoot, in the edit. That is your "tell the app who is in which stage" screen, and turning it off returns you to reading the numbers the three sub-tabs hold.

Production membership already has a store for this (p.onShoot). Pre and Post would each get the matching one, so somebody can be booked onto the edit before anyone knows how many days it will run — which is the exact case p.onShoot exists for on the shoot.

Two collisions, found by building it

Both are the filter fighting stage mode, and both resolve on the same principle: a control you are using must never be the thing that disappears. Switch Production off and then turn on Stage mode in the draft above to see them handled.

a. The column you'd tick was being hidden. With Production switched off its column goes — so in stage mode there'd be no box left to put anyone onto the shoot. So in stage mode all three columns always show, whatever the filter says. The filter only ever hides a read-only count.

b. Unticking somebody made their row vanish. Take them out of a phase and the filter would drop the row, taking the undo with it. So stage mode lists everyone and ignores the row filter. Turn stage mode off and the filter bites again.

Three decisions I'd rather not guess

Q1 · Does Budget's Per Person view stay?

Once Roles carries all this, Per Person is the same table minus the editing — and two near-identical tables are exactly what drifts apart. Building it once and having Budget's Per Person tab render the same function is the cheap answer, and the codebase already does this trick for Pre-Prod and Post, which are one screen rendered twice.

Q2 · How wide should Roles go?

The full Budget column set is thirteen columns and scrolls sideways on a laptop — you can feel it in the draft with £££ on. Roles is a screen you work in all day, so it may want to stay narrower than a costing report.
